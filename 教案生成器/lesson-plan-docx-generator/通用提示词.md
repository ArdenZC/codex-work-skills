# 教案生成器通用提示词 2.3.1

先完整阅读同目录 `SKILL.md` 和课程合同。新任务默认写 Lesson Content Contract 2.4；已有 Content 2.2/2.3 必须维持原语义，不静默升级。2.4 用独立 generation-evidence sidecar 强制校验检索、项目协作和逐课对照，不改 Lesson 阶段或评分 schema。

主 Agent 一次性用中文确认课程名称、专业、授课对象、总课时、理论/实践学时、组织方式、单课学时、教材、参考资料和是否需要实践任务工单。确认后主 Agent 冻结事实和全课程 outline（项目划分、每课主题/课时/类型、先修、贯穿案例及产出），再按项目分配专属子 Agent；每名 Agent 负责项目内全部理论和实践课、检索研究、编写、逐课对照、必要修订与自检。若当前会话不支持子 Agent，按项目包顺序执行并记录 fallback。主 Agent 最后统一校验 ID/课时/跨项目衔接与一致性、必要退回项目、合并并调用唯一 Word/PDF 生成器和 QA。子 Agent 不得改全局大纲、其他项目或最终 Word。不可确认的来源不得补造。

处理评价表可读性时只改视觉排版/QA；完整保留原评价字段，不清空、重分配、重算或重新解释得分、维度和评分政策。不得把预填分数本身判为缺陷。若布局修复需要改变固定模板，先列出最小兼容方案，不擅改 Template 1.1.2 或缩小字号。

Content 2.4 的强制日常流程是在课程基本盘与全课程项目 outline 冻结后、写第一版前，每项目实际检索免费公开的真实完整优秀/示范教案并打开阅读。按 `exemplar_contract.py` 的来源身份、作品分组、设计/学生活动/学习证据模式和 `do_not_copy` 思路记录来源。`QUALIFIED` 只表示来源和结构符合 Exemplar Contract 的资格要求，不代表教学优秀；没有获奖或正式优秀认定证明，本身不妨碍结构合格来源成为 `QUALIFIED`，也不得虚构荣誉。`QUALITY_ELIGIBLE` 是独立质量准入，须按 `benchmark_quality_eligibility.py` 及其文档的六项评估，用对应证据支持权威性/优秀性（含合同要求的认可证据）、课程相关性、学习者相关性、教学情境相关性、模式证据充分度和可迁移性；不得只凭 Tier A、机构权威或单一荣誉作出该判断。记录真实 URL、机构/作者、题名、检索日期、实际阅读范围、优秀性依据（如有）、可迁移方法与限制；不得把普通知识页、教学大纲、获奖名单或搜索摘要称为完整优秀教案，也不得编造来源、荣誉或阅读经历。检索状态必须区分：从未执行或跳过时标记 `ONLINE_EXEMPLAR_SEARCH_NOT_EXECUTED`（Evidence `status=not_executed`），正式生成证据门禁拒绝；已尝试但联网/检索工具受阻时记录 `search_blocked` 和实际阻断，也不得通过门禁；确已搜索但没有可靠优秀教案时记录真实 query 与结果，可用真实可读的普通教学设计作有限对照并标 `not_proven`，或如实记为 `searched_no_qualified_exemplar` / `searched_no_accessible_design`。这些状态不能互相替代；检索后未找到可靠优秀教案不等于没有执行检索。若搜索后没有任何可读设计，按受限证据记录，不得报告 `evidence_complete` 或通过最终 Acceptance。

先把抽象案例模式转为当前课的任务、师生行动、可观察产出/学习证据、形成性检查与适当支架，课程事实仍以已确认资料为准。完成第一版 Content 和 `pedagogical_review` 后、正式 Word 生成前，对照相关公开案例并逐项检查 `schemas/benchmark-lesson-review.schema.json` 中的 15 个维度。报告已有有效设计、真实差距、证据、适用性及是否值得改；普通路径必须标明“日常非盲对照”，不得声称独立 Reviewer、盲审、正式 A/B、`BENCHMARK_REVIEW_COMPLETE` 或 Authorization 通过。

每课初稿完成后必须逐项对照已有 15 维 rubric，写明已有设计、实际差距、证据和改进理由；只有发现实质问题时才修订，至多一轮实质性修订，并保存复审，否则保留初稿。固定顺序为：写前搜索 → 编写初稿 → 写后 15 维对照 → 必要时至多一轮实质性修订 → Word 生成。2.4 的执行记录写在强制 generation-evidence sidecar 中，并与每课内容摘要绑定。对照只标“日常非盲对照”，不得伪装正式 Quality Eligibility / A/B / Authorization。历史 Content 2.2/2.3 继续用其原有 `pedagogical_review` 与 digest 合同。最终 Word 仍只由 canonical `generate_lesson_plans.py` 生成并通过已有 QA。

Content 2.4 新课必须按 `total_hours` 完整生成 Lesson。`theory_only`、`practice_only`、`separate_full_lessons`、`integrated_lessons` 与 `hybrid` 全部覆盖课程总学时；`separate_full_lessons` 将理论课与实践课分别成课。只有历史 Content 2.2/2.3 的 `split_lessons` 仍只覆盖理论学时，历史 `practice_only` 仍为零 Lesson。整课数量按默认单课学时向上取整，最后一课保留真实余数；每课和理论/实践/总账必须准确相加。

64 总学时、32 理论、32 实践、默认每课 2 学时的 integrated 课程必须写 32 个 Lesson、覆盖 64 学时。不要因为用户不需要 WorkOrder 就删掉 Lesson 内实践：工单 false 仍是 32 Lesson/0 Practice Task；工单 true 仍是 32 Lesson，并提供 16 个 2 学时 Practice Task/WorkOrder。工单是 Lesson 实践环节的配套执行材料，不增加课程总时数。Content 2.2 的历史理论-only 语义不变；Content 2.3 split 也继续仅覆盖理论学时，Content 2.4 使用 `separate_full_lessons`（理实分开）、`practice_only`（纯实践）均覆盖全部学时；旧 Content 2.3 split 与 practice_only 不变。40 学时/默认每课 2 学时：纯理论 20 份；20+20 理实分开共 20 份（10 理论+10实践）；纯实践 20 份实践教案。

只有用户明确需要工单时才写 Practice Task Contract 1.1。Content 2.3 中，工单关闭时 Lesson 的 `practice_task_ids` 全为空；开启时 theory Lesson 为空，实践承载的 integrated/practice Lesson 与任务双向链接。Split 继续使用 task→theory 单向链接。WorkOrder Skill Agent 独立创作工单；Lesson Python 不得调用其 Python 或伪造工单文件。

正式 Benchmark 按 `SKILL.md` 固定流程处理：Curator 独占完整 Catalog/Split，Author/Reviewer 每课只接收选定 Cards；逐课 Review、课程汇总、Authorization claims 和 Artifact manifest 保持全链校验。Authorization 1.0 仍仅支持其既有 Content 2.2/2.3 边界；Content 2.4 普通生成的日常非盲逐课对照使用 `generation-evidence.json`，不得伪装为正式 A/B/Authorization。Round 2 必须是真实语义修订并更新对应的 review history/provenance。

正文、九阶段活动、学生证据、评价和反思由 Agent 创作。Python 仅校验确定性字段、课时账、来源、模板、输出、事务和渲染证据，不为内容补写 prose，也不判教学质量。按 `SKILL.md` 完成 Content QA、模板/输出 QA、请求的 render smoke 与 Acceptance 证据。
参考资料按“已确认的课程教材/教师提供的正式中文资料 → 中文专业或高职教材 → 实际读到相关内容的权威中文教学资料 → 必要且相关的英文原始资料”优先检索。逐条核对真实作者/编者、书名、版次、出版社和出版年或 ISBN（如适用），记录来源页和实际读取范围；只看到目录时只声明目录层面的主题匹配，不声称读过完整章节。来源不够可靠或不相关时少写并报告缺口，不为每课凑第二条来源。

图论教案要把图的有向/无向约定、邻居访问顺序和实际输入图写清，并执行核验遍历序列及边删除后的连通分量；至少检查任意单边删除和所声称的断边集合，测试输入必须能复现文字结论。教学语言避免跨课套用“本阶段聚焦 X / 教师围绕 X / 学生针对 X / 本阶段核验 X”四段式，写清本课问题、学生作品、教师反馈和成功标准，同时保留必要解释与支架。

QA 报告分开列出 `CONTENT`、`TEMPLATE_STRUCTURE`、`PDF_RENDER`、`VISUAL_READABILITY`、`SUBJECT_CORRECTNESS`、`REFERENCES`、`CROSS_FILE_ALIGNMENT`。PDF render smoke 不等于视觉可读性或学科/来源检查通过；用现有 Visual Sampling / Review Packet 检查评价表实际跨页、备注列换行和尾页留白，不新增 Authority 或付费服务。
Agent 只创作 Lesson Content JSON、Practice Task handoff data、Benchmark sidecars/evidence 与 pedagogical review。最终 Lesson DOCX 只允许由 canonical generate_lesson_plans.py 基于 Template 1.1.2 生成并通过 Output QA、所需 retained render、artifact manifest verification 与 Acceptance；任一 generator/template validation/Output QA/manifest verification 失败即 BLOCKED，禁止手工创建、修改、修补或绕过。完整禁令见 SKILL.md「最终 Lesson DOCX 的不可绕过生产边界」。

## Lifecycle candidate / practice_only 路由

LIF-01～05 已合并，当前仍是 Lesson Skill **2.3.1 candidate / pre-2.4 release state**，尚未发布 2.4 Stable。Canonical Lesson lifecycle 的完整生产路径为：

```text
Source Truth → Quality Eligibility / Benchmark Preparation → Content → Preproduction QA → Benchmark disposition / Review → Deterministic Teacher Review Packet → Human Teacher Review → Production Authorization → Canonical Generator → Artifact QA → Deterministic Visual Review Packet → Human Visual Review → Acceptance 3.0 → ACCEPTED
```

两处 Human Review 都必须由外部人工提供；synthetic evidence 只证明 contract closure，不代表真实教学质量通过。`production_pass` 是 generator 产物事务结果，不能替代 lifecycle `ACCEPTED`。

Content 2.3 的 `practice_only → lessons=[]` 继续合法；Content 2.4 改为必须全覆盖实践 Lesson。Canonical Lesson pipeline 的 PREVIEW/PRODUCTION 均只适用于至少 1 个真实 Lesson；`bind-content` 在绑定 Content 或推进 AUTHORING_COMPLETE 前明确拒绝 zero-Lesson，不能伪造 Lesson、Teacher Packet/Review 或 Lesson DOCX。Standalone Content tooling/direct generator 的历史行为保持兼容。需要纯实践材料时交给 Practice Task / WorkOrder Skill；Lesson Acceptance 3.0 不用于证明纯实践工单的教学验收，也不宣称 WorkOrder 已有等价生命周期。工单仍只在用户明确需要时创作。

完整边界与剩余发布事项见 `SKILL.md` 的 Lifecycle candidate / practice_only 路由；完整引擎包含对应的 pipeline、Acceptance 和 Release Closeout 文档。
